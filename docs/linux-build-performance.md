## 实际瓶颈与保留的修改

上一轮在 Linux 新输出目录完成 35 输入、33 个 core providers、60 个数据库阶段及 semantic 阶段，进程耗时 **1:19:54**。semantic 构建占 **2,131.08 秒**，是最大的单项；R0 约 508 秒，Research index 约 429 秒。这些时间来自实际阶段记录，不能将全部等待归因于 SQLite。

仅保留两个小型优化：

- 按文本字符长度稳定组批，减少 ONNX 推理的 padding；计算后写回原物理 vector ID，不改变窗口、文本或 occurrence，不合并重复字符串。
- Linux 默认最多使用 4 个 affinity 可见 CPU 线程。其他平台保持 2 个；`--embedding-threads` 可显式降低构建占用。ANN 仍按原物理顺序、单线程插入；查询模型的线程预算仍为 2。

构建参数和 embedding/ANN 耗时写入 `semantic/build.json`，线程进入恢复身份。没有更换模型、精度、ANN 参数、来源筛选、parser、合同、证据 ref 或证明规则；默认查询仍为 literal。

## 明确未采用的索引实验

针对原索引构建的 RAM 峰值，串行试验了两种写盘方式。三组均从相同 35 个已封存输入新建索引，运行内存完整 oracle 和独立落盘完整来源 oracle；随后逐行比较全部七张逻辑表，不只抽样或比计数。

| 方案 | builder + 内存 oracle 秒 | 含落盘 oracle 秒 | max RSS KiB | 决定 |
|---|---:|---:|---:|---|
| 原 RAM VACUUM + backup | 415.519 | 605.544 | 14,408,160 | 保持原实现 |
| VACUUM INTO | 523.762 | 704.423 | 8,318,740 | 来源等价但更慢，撤回 |
| 不压实，直接 backup | 506.440 | 703.032 | 8,318,992 | 来源等价但更慢且文件增大，撤回 |

因此最终 `scripts/builders/research_dataset.py` 与基础提交完全相同，不宣称整库内存下降。整库仍需约 16 GB RAM + 4 GB swap 级别资源。三个本轮可重建、已关闭的试验副本在完成来源/行集核验后退出留存；原合格索引、所有失败和测量报告保留。中间代码与撤回在 Git 提交中可追查。
